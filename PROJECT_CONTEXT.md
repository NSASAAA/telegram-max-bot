# Project Context

## Проект

`telegram-max-bot` — Python-проект бота для Telegram с перспективой добавления MAX.

Текущий практический фокус: Telegram-бот на VPS, который работает с корпусом статей Дзена заказчика, хранит материалы и изображения в SQLite/media-папке и показывает их пользователю через команды, включая первичную навигацию по тематическим рубрикам.

Долгосрочная цель: сделать не просто репостер статей, а коммуникационную систему вокруг автора и его аудитории.

Текущий runtime проекта — VPS. Локально на Mac мы пишем код, готовим данные, делаем коммиты и push в GitHub, но Telegram-бота локально не запускаем. Проверка пользовательских команд выполняется на VPS-боте после деплоя.

## Продуктовая идея

Изначальная идея: автоматически перепубликовывать статьи из Яндекс Дзена в Telegram, а позже в MAX.

После обсуждения концепция расширена: бот должен стать точкой контакта между автором и читателями. Статьи являются поводом для общения, а не конечной целью.

Будущий бот должен помогать:

- показывать новые статьи;
- находить материалы автора;
- собирать вопросы читателей;
- принимать отклики на статьи;
- собирать предложения тем;
- принимать истории читателей;
- показывать ответы автора;
- поддерживать проект.

Тематика автора: вера, семья, воспитание, материнство, боль, личные границы, психологическая зрелость, социальные роли, феминизм, свобода от разрушительных установок.

Бот не должен превращаться в простой "православный календарь" или пассивный архив. Более точное позиционирование: проводник по текстам автора и канал живой обратной связи.

## Аналитика автора и блога

Первичный анализ корпуса показал, что проект не стоит понимать как обычный православный блог, календарь, сборник благочестивых заметок или технический репостинг Дзена.

Более точное смысловое ядро:

```text
Честный женский разговор о вере, семье, болезни, браке, материнстве,
личных границах и праве не разрушать себя ради чужих ожиданий.
```

Авторская позиция строится на важном напряжении:

- автор находится внутри православной среды и говорит из нее;
- одновременно автор не поддерживает глянцевую картинку "правильной матушки", "идеальной жены", "терпеливой женщины" или "святой семьи";
- вера в текстах не выглядит декорацией, но и не используется как инструмент давления;
- автор часто сопротивляется подмене смирения самоуничтожением;
- личная боль, болезнь мужа, семейная нагрузка и опыт материнства становятся не темой жалобы, а способом говорить с читателем честно.

Авторский голос:

- личный;
- прямой;
- разговорный;
- полемичный;
- эмоционально честный;
- иногда резкий;
- не наставнический в классическом смысле;
- часто построенный как диалог с читателем;
- ориентированный на снятие фальши и "правильной картинки".

Психологически авторский контракт с читателем можно описать так:

```text
Здесь можно говорить о том, о чем неудобно говорить в красивой,
правильной и благочестивой картинке жизни.
```

Для проекта это принципиально важно: бот не должен стать сухим каталогом статей. Он должен поддерживать живую интонацию автора и помогать читателю найти текст, вопрос, отклик или разговор, который соответствует его реальной жизненной ситуации.

## Основные тематические линии

### Рассеянный склероз, болезнь мужа, инвалидность

Это одна из самых сильных и узнаваемых линий блога. Читателям важны не только факты о болезни, но и опыт жизни рядом с хроническим диагнозом: быт, страх, усталость, любовь, ограничения, принятие, семейные решения.

Эта линия может стать отдельной навигационной рубрикой в боте:

```text
Жизнь рядом с РС
```

### Брак и семья под давлением реальности

В блоге много текстов о браке не как об идеальной форме, а как о живом союзе, где есть болезнь, усталость, дети, деньги, быт, сложные решения и невозможность соответствовать чужим ожиданиям.

Важный фокус: не "как построить идеальную семью", а "как жить в реальной семье, где все сложнее, чем принято показывать".

### Женская роль, самопожертвование, феминизм

Очень важная и перспективная линия. Автор говорит с женщинами, которые устали от требований быть удобными, терпеливыми, спасательницами, хранительницами всего и при этом не иметь права на усталость, злость или собственную жизнь.

Возможная рубрика:

```text
Женщина не обязана
```

### Психология, границы, травма, эмоциональная зрелость

В корпусе заметно много текстов, где личный опыт соединяется с психологическим языком: границы, нарциссизм, травма, созависимость, алекситимия, эмоциональная зрелость, вина, стыд, принятие.

Эта линия хорошо подходит для будущей навигации в боте, потому что читатель часто приходит не за датой публикации, а за ответом на внутреннее состояние.

### Дети, подростки, воспитание, образование

Большая часть корпуса так или иначе связана с детьми, подростками, семейным укладом, школой, домашним обучением, сыновьями и самостоятельностью.

Перспективная подача: не абстрактные советы по воспитанию, а честный родительский опыт без идеализации.

### Православие без насилия над собой

Православие в блоге важно, но сильнее всего оно работает не как отдельная справочная тема, а в связке с реальной жизнью: семья, болезнь, вина, смирение, женская роль, церковные стереотипы.

Возможная рубрика:

```text
Вера без насилия над собой
```

### Москва, экскурсии, культура, мягкий лайфстайл

Это более спокойная и потенциально монетизируемая ветка. Она может быть полезна для расширения аудитории, мягкого вовлечения и возможных будущих продуктов автора: прогулки, экскурсии, подборки мест, культурные маршруты, личный взгляд на город.

## Метрики и интерес аудитории

По всем `440` материалам удалось извлечь просмотры:


Предварительные выводы по метрикам:

- лучше всего срабатывают не абстрактные православные темы, а личные, болезненные и конфликтные тексты;
- сильные заголовки часто содержат напряжение, вопрос, боль, семейную дилемму или обещание личного признания;
- тема РС и жизни рядом с болезнью является одним из главных драйверов внимания;
- темы брака, женской роли, самопожертвования и психологических границ выглядят сильными для удержания аудитории;
- интерактивные тексты и вопросы к аудитории могут собирать много комментариев даже при умеренных просмотрах;
- комментарии и просмотры измеряют разные типы интереса: просмотры показывают охват, комментарии показывают готовность вступить в отношения с автором.

Пример важного сигнала: статья `А как вы познакомились с мужем?` имела умеренные просмотры, но собрала много комментариев. Это означает, что простые личные вопросы могут быть сильным инструментом вовлечения.

## Гипотеза об аудитории

Вероятная центральная аудитория:

- женщины примерно `30-55`;
- замужние женщины или женщины с опытом сложных отношений;
- матери подростков или взрослых детей;
- читательницы из православной или околоцерковной среды;
- люди, уставшие от идеализированных образов семьи, веры и женственности;
- люди рядом с хронической болезнью, инвалидностью или тяжелым уходом;
- читатели, которым важен честный язык о вине, усталости, любви, границах и принятии.

Главные потребности аудитории:

- узнать себя в чужом опыте;
- получить разрешение не быть идеальной;
- найти язык для своей усталости, боли или злости;
- увидеть православную идентичность без давления и морализаторства;
- понять, где заканчивается смирение и начинается разрушение себя;
- почувствовать, что автор не сверху, а рядом;
- задать вопрос, рассказать свою историю, получить отклик.

Для удержания аудитории важно не только публиковать статьи, но и регулярно создавать ощущение разговора:

- вопросы к читателям;
- сбор историй;
- ответы автора;
- разборы писем;
- продолжения по мотивам комментариев;
- голосования по будущим темам;
- подборки старых текстов под актуальные жизненные ситуации.

## Продуктовое позиционирование после анализа

Бот должен развиваться как коммуникационная система вокруг автора, а не как техническая витрина Дзена.

Рабочее позиционирование:

```text
Бот "С матушкой за чаем" помогает читателю найти честные тексты
о вере, семье, болезни, браке, детях, женской роли и личных границах,
а также задать вопрос автору или откликнуться своей историей.
```

Важный принцип: статьи - это не финальная точка. Статьи являются поводом для общения.

Будущая петля вовлечения:

```text
Автор публикует текст
→ бот доставляет или рекомендует текст
→ читатель реагирует, задает вопрос или рассказывает историю
→ автор выбирает важные отклики
→ появляется новый текст, ответ или подборка
→ читатель видит, что его услышали
→ лояльность растет
```

## Контентная стратегия

Предварительный баланс будущего контента:

- `60%` - личные проблемные эссе: болезнь, брак, дети, вера, женская роль;
- `20%` - объясняющие тексты: РС, уход, семейные решения, психологические понятия;
- `10%` - интерактивные посты: вопросы, голосования, просьбы поделиться опытом;
- `10%` - мягкий лайфстайл: Москва, культура, прогулки, книги, кино, быт.

Сильные типы заголовков:

- личное признание;
- болезненный вопрос;
- семейная дилемма;
- конфликт между ожиданием и реальностью;
- конкретный опыт рядом с РС;
- разворот против привычного стереотипа;
- вопрос к читателю.

Слабее как самостоятельный двигатель роста могут работать слишком общие темы без личного напряжения: поздравления, нейтральные заметки, отвлеченные бытовые записи. Их можно оставлять для поддержания тепла, но не делать на них основную ставку продвижения.

## Аналитические и этические ограничения

Темы проекта чувствительные: болезнь, инвалидность, вера, брак, психологические травмы, семейные конфликты, женская роль.

Поэтому в будущей логике бота важно:

- не выдавать медицинские советы от имени бота;
- не ставить психологические диагнозы читателям;
- не заменять консультацию специалиста;
- аккуратно обрабатывать личные истории;
- не публиковать пользовательские вопросы без согласия;
- дать автору возможность модерировать входящие отклики;
- сохранять тон проекта: честно, прямо, но без эксплуатации чужой боли.

## Архитектурный принцип

Бизнес-логика не должна зависеть напрямую от Telegram или MAX.

Правильная схема:

```text
Telegram API ─┐
              ├── adapters → core → storage/services
MAX API      ─┘
```

`core/` содержит общую бизнес-логику.

`adapters/telegram.py` только принимает Telegram-события, преобразует их во внутренние модели и отправляет ответы.

`adapters/max.py` пока остается заглушкой. MAX будет добавлен позже как второй транспорт.

## Текущее состояние приложения

Сейчас работает Telegram-бот через `python-telegram-bot`.

Команды:

- `/start` — приветствие и основные команды;
- `/help` — список команд;
- `/about` — описание тестовой версии бота;
- `/articles` — последние статьи из SQLite-базы;
- `/top` — самые читаемые статьи из базы;
- `/random` — случайная статья;
- `/topics` — список тематических рубрик;
- `/topic <код>` — статьи выбранной рубрики;
- обычный текст — простой ответ о полученном сообщении.

`main.py` только загружает конфиг и запускает `TelegramAdapter`.

`config.py` загружает `.env` через `python-dotenv` и требует `TELEGRAM_BOT_TOKEN`.

`core/bot.py` содержит бизнес-логику команд.

`adapters/telegram.py` содержит Telegram-интеграцию и маршрутизацию команд.

`adapters/max.py` пока заглушка.

Локальная база `data/dzen_bot.db` остается только как заготовка/копия для анализа и возможной пересборки. Локальная старая `data/bot.db` с Хабром удалена, чтобы не путать ее с актуальной серверной базой.

RSS-контур (`rss_client.py`, `rss_import.py`, скрытая техническая команда `/check`) остается в коде как исторически реализованный механизм и возможная заготовка на будущее, но сейчас не является рабочим источником данных проекта.

Хабр больше не используется. Он был только учебным тестовым источником для проверки схемы:

```text

```

После перехода на корпус Дзена тестовая RSS-лента Хабра отключена и не должна попадать в текущую базу проекта.

На VPS папка `data/` подключена в контейнер как volume:

```text
/opt/bots/telegram-max-bot/data → /app/data
```

Файл базы `data/bot.db` на VPS виден контейнеру как `/app/data/bot.db`.

Текущий серверный `.env` после перехода на Дзен:

```env
SOURCE_RSS_URL=
CHECK_INTERVAL_SECONDS=0
DATABASE_PATH=data/bot.db
```

RSS-импорт поддерживается кодом в двух режимах, но сейчас выключен:

- ручной запуск, если он снова понадобится:

```bash
cd /opt/bots/telegram-max-bot
docker compose exec -T bot python -m telegram_max_bot.rss_import
```

- фоновый автоимпорт в процессе бота:
  - если задан `SOURCE_RSS_URL`;
  - и `CHECK_INTERVAL_SECONDS > 0`;
  - цикл импорта запускается внутри `TelegramAdapter` через `post_init`.

Текущая модель статьи в базе:

```text

link

updated
```

Тематическая разметка хранится отдельно:

```text
article_topics

```

`article_topics` связывает статьи с рубриками и хранит `topic_code` и `score`. `app_meta` хранит служебную сигнатуру индекса рубрик, чтобы бот мог автоматически пересобрать разметку, если поменялся корпус статей или версия классификатора.

Текущие рубрики:

```text
rs          Жизнь рядом с РС
family      Брак и семья
children    Дети и воспитание
women       Женская роль и границы
psychology  Психология
faith       Вера без насилия
daily       Быт и повседневность
culture     Москва и культура
```

Разметка пока первичная: она строится по ключевым словам из заголовка, summary, полного текста и категорий. Это MVP-слой для навигации; позже его нужно проверить вручную и улучшить.

Текущая синхронизация при импорте:

- новая статья → создается запись (`created`);
- существующая статья с измененным `content_hash` → обновляется (`updated`);
- существующая без изменений → обновляется только `last_seen_at` (`unchanged`).

На текущем этапе SQLite — осознанный простой выбор: база хранится как файл `data/bot.db` на VPS и подключается в контейнер через volume.

Будущая задача на более зрелом этапе проекта: рассмотреть миграцию с SQLite на PostgreSQL, если появятся несколько воркеров/контейнеров, много параллельных записей, админка, сложная аналитика или потребность в более надежной серверной базе данных.

## Рекомендуемый рабочий процесс

Разработка ведется локально на Mac, но Telegram-бот локально не запускается.

VPS сейчас является общим тестовым runtime проекта: на нем постоянно работает бот, и именно там проверяются команды после деплоя.

Обычный цикл:

```text
1. Сформулировать маленькую задачу.
2. Изменить код.
3. Проверить синтаксис/бизнес-логику локально без запуска Telegram polling.
4. Проверить git status.
5. Сделать commit.
6. Сделать push.
7. Дождаться GitHub Actions.
8. Проверить работу бота в Telegram через VPS-экземпляр.
```

Команды локально:

```bash
cd /Users/aleksandr_maraenko/Desktop/telegram-max-bot
git status
PYTHONPATH=src python -m compileall src
git add .
git commit -m "message"
git push
```

Не запускать локально:

```bash
PYTHONPATH=src python -m telegram_max_bot.main
docker compose up -d --build
```

Причина: локально и на VPS используется один Telegram token, поэтому два polling-процесса будут конфликтовать.
